# Testing a CRUD REST API end-to-end

By the end of this recipe you'll have full coverage of a CRUD
resource: POST (create), GET-list, GET-single, PATCH (update),
DELETE. Five declarations, ~80–100 generated test cases, running
against a real public API in seconds.

We'll target [JSONPlaceholder](https://jsonplaceholder.typicode.com/)
(`/posts`) — a public fake REST API that genuinely accepts CRUD
operations (though it doesn't persist them; that's fine, our
assertions verify shape and echo, not persistence).

---

## What you'll have when you're done

```
crud-tests/
├── apiwright.config.json
├── environments/
│   └── qa.yaml
└── tests/
  └── posts/
    ├── create.endpoint.json
    ├── list.endpoint.json
    ├── get.endpoint.json

    └── delete.endpoint.json
```

Five declarations expanding to ~80–100 generated cases (smoke +
regression) covering every method's HTTP correctness, schema
conformance, auth (skipped — public API), input validation, boundary
behaviour, idempotency for GET/DELETE, and your declared assertions.

## Step 1 — Project scaffold

```bash
mkdir -p crud-tests/tests/posts crud-tests/environments crud-tests/reports
cd crud-tests
```

Notice the `tests/posts/` subdirectory — declarations are grouped by
resource. As your suite grows, `tests/users/`, `tests/orders/`, etc.
mirror your API's resource hierarchy. CLI filters like
`--path tests/posts/` let you run "just the posts tests" later. See
[best-practices.md](../best-practices.md).

## Step 3 — POST (create)

`tests/posts/create.endpoint.json`:

```json
{
  "id": "posts.create",
  "name": "POST /posts — create a post",
  "method": "POST",
  "url": "/posts",
  "tags": ["posts", "write"],
  "markers": ["smoke"],
  "prod_safe": false,
  "request": {
    "headers": { "Content-Type": "application/json; charset=UTF-8" },
    "body_schema": {
      "type": "object",
      "required": ["title", "body", "userId"],
      "properties": {
        "title":  { "type": "string", "minLength": 1, "maxLength": 200 },
        "body":   { "type": "string", "minLength": 1, "maxLength": 5000 },
        "userId": { "type": "integer", "minimum": 1, "maximum": 1000 }
      }
    },
    "body_example": {
      "title":  "APIWright CRUD recipe — created post",
      "body":   "Generated by the APIWright CRUD cookbook walkthrough.",
      "userId": 1
    }
  },
  "response": {
    "expected_status": 201,
    "sla_ms": 5000,
    "schema": {
      "type": "object",
      "required": ["id", "title", "body", "userId"],
      "properties": {
        "id":     { "type": "integer", "minimum": 1 },
        "title":  { "type": "string" },
        "body":   { "type": "string" },
        "userId": { "type": "integer" }
      }
    }
  },
  "assertions": [
    "response.body.title  equals request.body.title",
    "response.body.body   equals request.body.body",
    "response.body.userId equals request.body.userId",
    "response.body.id     exists"
  ]
}
```

What this single declaration generates under `--markers smoke,regression`:

- 4 universal cases (status / content-type / schema / sla)
- 4 declared assertions
- 1 `method_not_allowed` (regression)
- 1 `malformed_json_returns_400` (regression — `body_example` is
  present, so APIWright sends `{"unterminated:` as a body)
- 3 `required_field_omission_returns_400` (regression — one per
  required field: title, body, userId)
- 3 `type_violation_returns_400` (regression — one per typed field)
- ~6 `boundary_battery` cases (regression — minLength/maxLength on
  title and body, minimum/maximum on userId)

**~22 cases from this single declaration.** All cases share the same
declared baseline; the catalog mutates it per case type.

## Step 4 — GET (list)

`tests/posts/list.endpoint.json`:

```json
{
  "id": "posts.list",
  "name": "GET /posts — list all posts",
  "method": "GET",
  "url": "/posts",
  "tags": ["posts", "read"],
  "markers": ["smoke"],
  "request": {},
  "response": {
    "expected_status": 200,
    "sla_ms": 5000,
    "schema": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["id", "title", "body", "userId"]
      }
    }
  },
  "assertions": [
    "response.body count_greater_than 50"
  ]
}
```

Generates: 4 universal cases + 1 assertion + 1 method_not_allowed +
1 `get_idempotency` (regression — calls GET twice, asserts identical
results). ~7 cases.

The `count_greater_than` assertion on the response body works because
the body resolves to an array; the aggregate operator counts its
elements. See [assertions.md](../assertions.md).

## Step 5 — GET (single)

`tests/posts/get.endpoint.json`:

```json
{
  "id": "posts.get",
  "name": "GET /posts/1 — get a single post",
  "method": "GET",
  "url": "/posts/1",
  "tags": ["posts", "read"],
  "markers": ["smoke"],
  "request": {},
  "response": {
    "expected_status": 200,
    "sla_ms": 5000,
    "schema": {
      "type": "object",
      "required": ["id", "title", "body", "userId"],
      "properties": {
        "id": { "type": "integer", "const": 1 }
      }
    }
  },
  "assertions": [
    "response.body.id     equals 1",
    "response.body.userId is_not_null"
  ]
}
```

Similar to list but for a single resource. Hard-coded path parameter
(`/posts/1`) for now — APIWright v1.0 doesn't auto-discover or
parameterise across endpoints (that's a multi-step flow, deferred to
v1.5).

## Step 6 — PATCH (update)

`tests/posts/update.endpoint.json`:

```json
{
  "id": "posts.update",
  "name": "PATCH /posts/1 — partially update a post",
  "method": "PATCH",
  "url": "/posts/1",
  "tags": ["posts", "write"],
  "markers": ["smoke"],
  "prod_safe": false,
  "request": {
    "headers": { "Content-Type": "application/json; charset=UTF-8" },
    "body_schema": {
      "type": "object",
      "properties": {
        "title": { "type": "string", "minLength": 1, "maxLength": 200 }
      }
    },
    "body_example": {
      "title": "APIWright CRUD recipe — updated title"
    }
  },
  "response": {
    "expected_status": 200,
    "sla_ms": 5000,
    "schema": {
      "type": "object",
      "required": ["id"],
      "properties": {
        "id":    { "type": "integer", "const": 1 },
        "title": { "type": "string" }
      }
    }
  },
  "assertions": [
    "response.body.id    equals 1",
    "response.body.title equals request.body.title"
  ]
}
```

PATCH semantics: partial update. No `required` fields in the
body schema (you can patch any subset). APIWright still generates
boundary cases for the constrained field (`title` minLength /
maxLength) and a type-violation case.

## Step 7 — DELETE

`tests/posts/delete.endpoint.json`:

```json
{
  "id": "posts.delete",
  "name": "DELETE /posts/1 — delete a post",
  "method": "DELETE",
  "url": "/posts/1",
  "tags": ["posts", "write", "destructive"],
  "markers": ["smoke"],
  "prod_safe": false,
  "request": {},
  "response": {
    "expected_status": 200,
    "sla_ms": 5000,
    "schema": { "type": "object" }
  }
}
```

Generates: 4 universal cases + 1 `method_not_allowed` + 1
`delete_idempotency` (regression — calls DELETE twice, asserts same
response shape). ~6 cases.

The `destructive` tag isn't used by APIWright itself but lets you
filter — `--exclude-tag destructive` is handy for production-readonly
sweeps.

## Step 9 — Run

Smoke pass (every PR):

```bash
apiwright validate ./tests
apiwright run --env qa --markers smoke
```

Expected: 5 endpoints planned, all passing, ~25–30 attempts total
(smoke generates 5–8 cases per endpoint depending on shape).

Full regression (nightly):

```bash
apiwright run --env qa --markers smoke,regression
```

Expected: same 5 endpoints, ~80–100 attempts total. The bulk comes
from `posts.create` and `posts.update` where the body_schema fields
each get required-omission, type-violation, and boundary cases.

## What just happened

From **5 declarations totalling ~250 lines** APIWright generated
**~80–100 test cases** covering:

- Status / content-type / schema / SLA on every endpoint (universal).
- Required-field omission for every required field in every body
  schema.
- Type-violation for every typed field in every body schema.
- Boundary battery (inside/outside) for every minLength/maxLength/
  minimum/maximum/enum constraint.
- Malformed JSON returning 400 for every endpoint with a body.
- Method-not-allowed for every endpoint.
- GET / DELETE idempotency.
- Every assertion you declared.

If you'd written these same ~100 tests by hand (Jest / pytest / etc.)
they'd be 2000+ lines of test code, take hours to author, and need
maintenance every time the API contract changes. With APIWright,
contract changes mean editing one declaration; the catalog
regenerates automatically.

This is the leverage [comparisons.md](../comparisons.md) talks about.
